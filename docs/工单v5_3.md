## 1. 撤回：stage4 残差下界（第二次更正）

v5.1 声称"MAP 选错 ⇒ 误差 ≥ 0.337 mm"，v5.2 保留了这个说法。**两次都是错的。**

残差的可达集**恰好就是 MAP 候选的 Voronoi 单元**，所以"MAP 不是最近候选"只意味着 GT 刚刚越过单元边界。正确的最小可达误差：

$$e_{\min}=\max\bigl(\lvert d_{gt}-d_{\mathrm{MAP}}\rvert-0.5\,\Delta_{\mathrm{MAP}},\ 0\bigr)$$

反例：候选 $\{0,1\}$，GT $=0.51$，MAP $=0$。MAP 确实不是最近候选，但残差可达 $+0.5$，最终误差 **0.01**，不是 0.5。误差随越界深度线性增长，**在边界处趋近于 0**。

连带作废：`0.5223 × 0.337 ≈ 0.176` 的量级分析；"用 ≤1.3% 的收益换 52% 的量化下限"这句结论。另外 `res_target_is_map` 的统计域是 `sup = valid & in_range`（`losses/composite.py:314`），只覆盖 GT 已落在 stage4 窗口内的像素，不是全体像素比例。

**本轮不动 stage4 head**（vNext 用的是 W0 的 `expect`，根本没有 MAP 残差头）。真要查，判据是 `map_residual_reachable_frac = P(\lvert d_{gt}-d_{\mathrm{MAP}}\rvert \le 0.5\Delta)`，不是 `res_target_is_map`。进 backlog。

## 2. 为什么删掉 Gate

保留 Gate 的代价不是那几次离线统计的算力，而是**它给了中间指标否决权**。一旦 G0-3 的某个分位数不达标就换 S2 的内容，模型的构成就由一串中间读数拼出来，而不是由"完整三维重建缺什么"决定。前三版工单每一版都在修上一版被中间指标带偏的地方，这本身就是证据。

因此：

- **G0-2（stage4 head 消融）、G0-3（中心策略）、G0-4（在线对齐）全部移出。** 它们保留为解释工具，但**不得决定本轮加什么模块**。
- **不再取回 W1 checkpoint，不评 W1 点云。** W1 的定位已经清楚（尾部更好、主体更差），而主干选择另有依据（§3.1）。
- **唯一前置评测是 W0 的 22 场景点云基线**，因为现有那组 0.3180 谱系不明（§6.1）。

P1（离散锚点）、stage4 head、在线先验对齐、P4（候选替换）、RCL、visibility 监督、range controller —— **全部进 backlog**，本轮一律不与 CVPE 同批试探。

## 4. CVPE 实现规格（已实现）

### 4.1 注入点：复用 FPN 现有的 p8 挂点

`models/fpn.py:106-111` 的 docstring 早就写着：DINO 注入在 **top-down 之前**，所以它沿 p8→p4→p2→p1 传遍四级。CVPE 挂同一处，传播由现有 `lateral_* + interpolate + smooth_*` 完成，**不需要 MonoMVSNet 那条平行的降维/上采样链**（`FMT_with_pathway`）——他们需要它只是因为 `FPN4` 是外部模块、拿不到 top-down 中间态。

实现是一个 `mid_hook`：`FPNFeatureExtractor.forward(x, dino, mid_hook)` 在 `p8 = lateral + dino` 之后调用它；`MultiViewFPN` 负责 `[B*V,…] ↔ [B,V,…]` 的形状转换；`mid_hook=None` 时前向**逐位不变**。

### 4.2 残差只加一次

`CrossViewPE.forward` **只返回 delta**，形状 `[B, V-1, 128, h8, w8]`。调用方（`models/network.py`）执行且只执行一次：

```python
return torch.cat([p8[:, :1], p8[:, 1:] + delta], dim=1)
```

**不用 `p8[:, 1:] = …` 原地赋值**（对 autograd 叶子原地写会静默丢梯度），reference 逐位不变。`out_proj` 零初始化 ⇒ step 0 的 `delta` 恒为 0 ⇒ 与 `cvpe=off` **逐位一致**（实测端到端 `max|Δ| = 0.000e+00`）。

### 4.3 结构写死

```text
通道        128 --1x1--> d_model=64 --CVPE--> --1x1--> 128 (out_proj 零初始化)
注意力      MonoMVSNet 的 ELU(x)+1 线性注意力, 不显式构造 NxN 矩阵
            (p8 在 640x896 下是 80x112 = 8960 token, softmax 的 N^2 放不下)
heads       8
层序        self,cross,self,cross,self,cross,self,cross   (固定, 不暴露)
每层        attn residual -> LayerNorm -> 2 层 FFN -> residual -> LayerNorm
平面        8 个全局逆深度均匀平面, 只服务位置编码, 与 48/16/8/4 无关
更新对象    只更新 source, reference 不变
```

深度平面：

$$v_j=\frac1{d_{\max}}+\frac{j}{D-1}\Bigl(\frac1{d_{\min}}-\frac1{d_{\max}}\Bigr),\qquad d_j=1/v_j,\quad D=8$$

### 4.4 双向几何位置编码

```text
source query = PE2D(source)    + encode(warp_ref_to_src, source_camera)
reference KV = PE2D(reference) + encode(warp_src_to_ref, reference_camera)
```

两个 warp 都调 `utils.geometry.homography_warp_features`，与 cost volume **同一个函数**——两处各写一份迟早分叉，而且分叉时两边都不报错。相机向量固定为

$$C=\operatorname{vec}\bigl(E^{-1}K_4^{-1}\bigr)\in\mathbb R^{16}$$

其中 $K$ 先按 `feature_stride=8` 缩放，与 warp 内部同一约定。

### 4.5 数值合同

```text
K/E 求逆、投影网格、深度平面   fp32 且 no_grad
grid_sample 的特征             训练 dtype (bf16)
相机 16 维向量的归一化与 MLP    fp32
线性注意力                     训练 dtype, LayerNorm/归约由 autocast 处理
```

**一处对 MonoMVSNet 的偏离**：相机向量的归一化用 `LayerNorm(16)` 而不是它的 `BatchNorm1d(16)`（`FMT_with_CVPE.py:143`）。三个理由，每条都是实打实的故障：

1. BN1d 在 **B=1 的训练前向**下直接抛 `Expected more than 1 value per channel`——`fit_batch.sh` 的显存扫描从 batch 1 起步，`--smoke` 也是，一上来就崩。**这是实现过程中实际触发的。**
2. 它把同一 batch 里不同样本的相机耦合在一起：训练用 batch 统计、推理用 running 统计，而推理恒为 B=1。同一对相机在训练和测试下拿到不同编码，**且不报错**。
3. 每个 source 要调两次（`cam_src` 与 `cam_ref`），两种分布被写进同一份 running stats；DDP 下各 rank 也不同步。

LayerNorm 逐样本，三条全不存在；16 个分量之间的量级差异（焦距 ~1e3 / 旋转 ~1 / 平移 ~1e2）由紧随其后的 `16→64` 全连接逐分量重新定标。

### 4.6 fingerprint 与显存

fingerprint 记录 `cvpe_enabled / d_model / num_planes / n_heads / cam_mid_channels / layer_pattern / feature_stride=8 / plane_space=inverse_global / align_corners=true`；`test.py` 从 fingerprint 恢复全部字段，缺字段的旧 checkpoint 恢复成 `enabled=False` 并 strict 加载成功。

参数量 +0.597 M（8.590 M → 9.188 M，DINO 关闭口径）。显存实测（本机 RTX 5060 Ti，B=1，bf16，dino=off）：

| 分辨率 | cvpe off | cvpe on | 增量 |
|---|---:|---:|---:|
| 512×640 | 6.68 GiB | 7.10 GiB | **+6.3%** |
| 640×896 | 11.65 GiB | 12.37 GiB | **+6.2%** |

**batch 已定死为 4**（umhpc 单卡 A100-80GB），不是待搜索的量。按 `gpu-memory-scaling-law` 记的 B=4 @ 640×896 峰值 ~51 GiB 外推，CVPE 约 +3.2 GiB → **~54 GiB / 80 GiB**，余量约 26 GiB。

**不要跑 `scripts/fit_batch.sh`。** 它是一个 batch 搜索（`BATCHES=1,2,4,5,6,7,8`），目的是"然后再决定 PER_GPU_BATCH"——而这个决定已经做了。更实际的风险是：它若"建议"另一个 batch，`_arm_common.sh` 的 sqrt 缩放会连带改掉 lr（B=4 对应 lr=4.243e-4），跑出来的就不是预注册的那个实验了。这正是本工单要消掉的漂移模式。

余量若判断错了，`sbatch` 提交后**几分钟内**就会 OOM 退出，代价只有排队时间——比先跑一次扫描再排队更省。

## 5. 训练侧的三处基础设施改动

### 5.1 梯度分组裁剪（`train.py`）

`conf_detach=True` 只切断了置信度头对深度特征的**梯度**，但全模型一次 `clip_grad_norm_` 会把它的范数算进总范数——于是"旁路头梯度大"就等比例缩小主干的更新步长。那样 W3-C 就不再是可加可减的旁路，而是一个悄悄改变主干学习率的东西。

改成两组分别裁剪（`conf_head.*` 与其余），主干的更新与 conf_head 开不开**严格无关**。新增曲线 `grad/norm_base_unclipped`、`grad/norm_conf_unclipped`。不拆成两个 optimizer——那会改变 AdamW 的 state 布局与 checkpoint 结构，而要解决的只是范数耦合。

### 5.2 `capped_2mm`：像素累加器里直接算

$$\mathrm{capped}_2=\frac1N\sum_i\min(e_i,\,2\ \mathrm{mm})$$

**不用 $\mathrm{body}_2\cdot\mathrm{acc}_2+2(1-\mathrm{acc}_2)$ 反算**——那个恒等式只在同一批像素上成立，拿两个各自平均过的日志标量去乘会引入窗口口径不一致的偏差。`WindowedMeter` 与 `_run_validation` 各加一个累加槽。

**措辞修正**：$\min(e,2)$ 对每个像素的误差**单调不减**，不是"必然变好"——20 mm → 3 mm 不计入。所以 `tail_frac_8mm` 必须始终并列汇报。

### 5.3 `risk@0.6`：与融合门控共用同一份排序信号

```text
每张验证图, 在 GT-valid 像素内:
    k = ceil(0.6 * n_valid)
    取 cascade_confidence 降序前 k 个, 累加 |pred - gt| 与计数
跨图: 按保留像素数加权求和后相除 (不是各图 risk 的简单平均 —— DTU 每张图的
      有效像素数差别很大, 简单平均会给小图过高权重)
排序信号固定: cascade_confidence(mode=product, window=1)
```

`cascade_confidence` 已从 `test.py` 移到 `models/fusion_conf.py`，`train.py` 与 `test.py` 从同一处导入（校验脚本断言三处是**同一个对象**）。否则"训练时量的排序"和"融合时用的排序"是两个东西，而 `risk@0.6` 的全部意义正是预测后者。

## 6. 融合与标定

### 6.1 点云基线必须重建

`log/pred_points_R_geo_dedup/`（2026-08-21）只有 `result.txt`，没有任何谱系记录；而 W0 的 checkpoint 是 08-24 才存的——**那组 acc 0.3708 / overall 0.3180 既不是 W0 也不是 W1**，却被当作"UPRMVS 当前水平"引用了三版工单。

从本版起，`test.py` 每次推理都往 `OUT/` 与 `PLY_DIR/` 写同一份 `run_manifest.json`（在推理**之前**写，跑到一半崩掉也留着谱系）：

```text

当前 git SHA + 工作树是否干净
prior cache 路径与 signature (三个历史位置都找, 找不到显式写 null)
NUM_VIEWS / RESIZE / FULL_IMAGE / MAX_REFS / split / scans

fusion backend / dedup 设置 / 评测工具路径与 git SHA / GT 路径 / 时间戳
```

**没有 manifest 的历史点云不得再作为基线。**

### 6.2 固定保留率，取代阈值扫描

新增 `--photo-keep-ratio`（默认 0 = 保持旧的固定阈值行为）。`>0` 时忽略 `--photo-thresh`，对每个参考视图：

```text
valid = isfinite(depth) & (depth > 0)
k = clamp(ceil(r * n_valid), 1, n_valid)
order = stable argsort(conf[valid], descending)      # 打平时结果可复现
photo_mask[valid[order[:k]]] = True
keep = photo_mask & (n_geo >= geo_views) & valid
```

为什么要它：阈值扫描是一条按中间指标逐项调参的支线；而且两个模型的置信度分布不同，同一个阈值下保留率不同——那时比较的就不只是深度质量。固定保留率把这个自由度消掉。

`gipuma` 后端的光度门在它自己的二进制里，给不出固定保留率，**同时启用直接报错**，不静默退回阈值（静默退回会产出名字一样、保留率完全不同的点云，而目录里看不出区别）。

### 6.3 二参数 Platt 标定

置信度损失用的是**类别平衡** BCE（`losses/composite.py`），加权会平移最优 logit 的截距，所以单参数温度不够——`prob=0.5` 并不表示"五成把握"。改成

$$p=\sigma(z/T+b),\qquad T>0$$

`FusionConfidenceHead` 新增 `calib_bias` buffer；旧 checkpoint 缺这个 key 时由 `_load_from_state_dict` 自动补 0，**仍然 strict 加载**（strict=False 会把真正的形状/命名错误一起放过去，比缺一个 buffer 危险得多）。

拟合用确定性的 CPU LBFGS（`max_iter=100`, `strong_wolfe`, 初值 `log_T=0, bias=0`, `log_T` 夹在 `[-5,5]`），目标是**未加权**的 BCE——校准要对齐的是真实正类频率，不是训练时为平衡梯度人为设定的频率。

`--write-out` 产出**一份新的** checkpoint，**不允许覆盖原文件**（覆盖之后就再也拿不到未标定的 logit，标定也就无法重做）。报告 `T / bias / ECE / Brier / AURC / risk@0.6` 的前后对比，并断言 **AURC 与 risk@0.6 在标定前后不变**（正斜率仿射不改变排序；容差取相对 1e-3 而不是 0，因为 sigmoid 在 fp32 下会把接近的 logit 映射成完全相等的概率，并列元素的先后可能变——那不是错误，而真正的实现错误会差好几个百分点）。

```text
   (脚本里的 mkdir -p logs 来不及)。sbatch_1gpu.sh 用的是同一个路径, 训练
   跑得起来就说明它在。
2. 测试集 prior 缓存齐全 —— 三步都用 BUILD_PRIORS=skip (缺了直接报错退出,
   这是有意的: 静默重建是 21 小时)。真报缺, 那一次改成 BUILD_PRIORS=auto 补差集。
3. DINOv3 权重在位 —— W0 的 fingerprint 是 dino_mode=all_view / spre_enabled=True,
   推理要加载它。训练用过就说明在。
```

### 7.2 W0 基线点云（一次）

```bash
WHICH=w0 sbatch scripts/sbatch_test_dtu.sh
```

**必须 `sbatch`，不能 `bash`。** `scripts/test_dtu.sh` 自己**没有 `#SBATCH` 头**——它是"在已经拿到卡的地方跑"的脚本：直接 `bash` 会跑在登录节点上（没有 GPU，而且这是几小时的作业），直接 `sbatch scripts/test_dtu.sh` 又拿不到 `--gres=gpu:1`。`scripts/sbatch_test_dtu.sh` 负责排队与环境，拿到卡之后再 `bash` 调它。

协议参数全部烘在包装脚本里（`RESIZE=0.8` 必须显式给，因为 `scripts/test_dtu.sh:58` 的默认是 1.0；`PRIOR_RESIZE` 与它**相互独立**——prior 按原生 1200×1600 建、推理时下采样——所以改 `RESIZE` **不需要** `BUILD_PRIORS=force`）。它与 §7.5 共用同一个 `case`，两条协议只差 checkpoint / 置信度来源 / 输出目录三个量，其余逐字相同——这是配对比较的前提。

不评 W1，不做五个困难场景的中间筛选。

### 7.3 唯一训练（一次）

```bash
PER_GPU_BATCH=4 ARM=vnext sbatch scripts/sbatch_1gpu.sh
```

**12k 不做胜负判定，不另开分支。** 只有 NaN、投影错误、OOM、代码结构错误才停止。这样不会因为新模块收敛速度不同而被 12k 误杀。

训练期只当护栏看的曲线：`cvpe/delta_rel`（0 或 ≫1 都要停下来看）、`grad/norm_base_unclipped` 与 `grad/norm_conf_unclipped`（后者压过前者说明分组裁剪没生效）、`val/capped_2mm`、`val/risk_at_0.6`。

### 7.4 标定（一次）

```bash
WHICH=calib sbatch scripts/sbatch_test_dtu.sh
```

**同样必须 `sbatch`。** `calibrate_conf.py` 是 `cuda if available else cpu`，在登录节点上会**静默**退回 CPU，然后拿 CPU 跑一整个 val split。

`--require-step 30000` 会断言 checkpoint 的 step——拿中途的 ckpt 标定再当终审，等于用另一个模型的置信度去解释这个模型。标定跑在 **val** split 上（不是 test——拿终审集拟合温度，那个终审就不独立了），并用与 §7.5 **同一套部署口径**（0.8 整幅 + 5 视角）：换了分辨率 logit 的分布就变了，拟合出来的 $(T,b)$ 对不上要用它的那次推理。

产出 `latest_calibrated.pth`（新文件，不覆盖原 ckpt）与一份报告，报告里 **AURC 与 risk@0.6 在标定前后必须不变**，变了直接报错退出。

### 7.5 vNext 点云（一次）

```bash
WHICH=vnext sbatch scripts/sbatch_test_dtu.sh
```

用的是**标定过的** ckpt（`latest_calibrated.pth`）+ `CONF_SOURCE=learned`；找不到就 fail fast，不会静默退回未标定的那份。

**禁止阈值扫描；禁止只评五个困难 scan 之后继续改模型。**

### 7.5b 打分（独立的第三步）

`test_dtu.sh` 只产 ply，**不打分**。两个目录各跑一次 Fast-DTU-Evaluation：

```bash
cd <Fast-DTU-Evaluation> && python eval_dtu.py --method mvsnet --save --pred_dir <PROJECT>/log/pred_points_W0_final --gt_dir <GT>
```

（`scripts/eval_pointcloud.sh` 是更早的包装，按 `pred_points_<arm>_<TAG>` 命名、且硬编码了 `PHOTO_THRESH`，与 v5.3 的 `_final` 目录和固定保留率对不上，本轮不用它。）

### 7.5c 终审判据

```bash
python scripts/compare_pointclouds.py --base log/pred_points_W0_final --cand log/pred_points_UPRMVS_vNext_final
```

### 7.5d 三条 sbatch 的依赖关系（不要一次全提）

```
训练(7.3) ──> WHICH=calib(7.4) ──产出 latest_calibrated.pth──> WHICH=vnext(7.5)

WHICH=w0(7.2) ── 独立支线, 与 vNext 无关, 随时可跑
```

`calib` 没跑完就提 `vnext`，会被 checkpoint 守卫拦下（这是**有意的**：不拦的话它会静默退回未标定的 `latest.pth`，`--conf-source learned` 读的就是未标定的 logit，`photo` 门失去物理含义，而且从点云结果上完全看不出来）。

不想守着的话用 slurm 依赖链，一次排完：

```bash
J1=$(squeue -h -o %i -n uprmvs_1gpu -u $USER | head -1)      # 正在跑的训练作业号
J2=$(WHICH=calib sbatch --parsable --dependency=afterok:$J1 scripts/sbatch_test_dtu.sh)
J3=$(WHICH=vnext sbatch --parsable --dependency=afterok:$J2 scripts/sbatch_test_dtu.sh)
WHICH=w0 sbatch scripts/sbatch_test_dtu.sh                    # 独立, 不用挂依赖
echo "calib=$J2  vnext=$J3"
```

`afterok` 表示前一步**成功退出**才启动：训练崩了、标定的保序断言没过，后面就不会拿着半成品继续跑。

### 7.6 checkpoint 选择规程

```text
终审统一用 latest.pth @ step 30000, W0 与 vNext 同一规则
best.pth 仍按 abs_err 选 (train.py 未改), 但**不参与点云 checkpoint 选择**
禁止用 test 集点云结果反向挑 checkpoint
```

`--best-metric` **没有实现**, 也不需要: 终审既然固定用 `latest.pth@30000`,
再造一个 `best_capped2.pth` 只是多一个不会被用到的文件。

为什么不把 `best.pth` 换成按 `capped_2mm` 选：`capped_2mm` 忽略所有超过 2 mm 的改善，本质上仍是主体精度的局部指标；把选择依据从 `abs_err` 换成它，只是从一种局部偏置换成另一种。用固定 step 最公平，也最省争论。

## 8. 验收

### 8.1 终端目标（点云为主，决定模型去留）

- $\Delta\mathrm{acc}\le-0.02$ mm（相对 §7.2 得到的 W0 基线，**不再引用谱系未知的 0.3708**）；
- $\Delta\mathrm{overall}<0$；
- comp 不显著退化——用 **22 场景逐场景配对 bootstrap**，不用主观判断；判据已**预先**钉进代码：

```bash
python scripts/compare_pointclouds.py --base log/pred_points_W0_final --cand log/pred_points_UPRMVS_vNext_final
```

  重采样单位是 **scan 而不是像素**（同一 scan 内的点不独立，按点重采样会把 CI 压得虚窄）；必须配对（22 个 scan 的难度差好几倍，各自算均值再相减的话方差被场景难度支配，根本分不出 0.02 mm）。脚本同时校验两边的 `run_manifest.json`：融合参数或推理参数不一致就直接告警，缺 manifest 就按 §6.1 拒绝当基线。

- scan48/77 报告均值与单场景结果，**不设"一场不改善就否决"的硬门**（单场景波动会误杀整体更好的模型）；
- scan29/33/49 只做结果分解，**不作为中途改模型的理由**。

### 8.2 深度图指标（只当护栏，不决定去留）

- `capped_2mm` 退化 ≤ 0.02 mm；
- `acc_2mm` 下降 ≤ 0.005；
- `tail_frac_8mm` 上升 ≤ 0.003。

### 8.3 机制解释（既不决定去留，也不许反过来改模型）

$w^{eff}=\Delta/p^{\max}$、FWHM、anchor 误差、各级 `in_range`：**只回答"CVPE 是不是真的锐化了匹配响应"**。即使它们全都没改善，只要最终点云整体显著变好，也不否决模型；反过来，它们好而点云不好，也不算通过。

## 9. 若 vNext 没赢

**不要立刻拆成三个 arm 逐项归因。** 那正是本工单要避免的模式。顺序是：

1. 先看护栏曲线定位是工程故障还是模型问题（`cvpe/delta_rel` 恒 0 = CVPE 没学到；`grad/norm_conf` 压过 base = 裁剪分组没生效；`capped_2mm` 在 12k 之前就崩 = 数值问题）；
2. 确认不是工程故障之后，**才**围绕这一个完整候选补最少量的**回顾性**消融（`--cvpe off` 单项），而不是在模型尚未赢之前逐项展开；
3. backlog 里的东西（P1 / stage4 head / 在线对齐 / P4 / RCL / range controller）按"它改的是不是 $w^{eff}$"排序，不按"哪个中间指标最难看"排序。

## 11. 一句话

前三版把"根因是匹配证据不够锐"这条判断建立起来了，但执行方案一直是按中间指标逐项递进的。v5.3 把它收缩成一条完整因果链、一次训练、一次终审：**CVPE 改匹配证据，geo_valid 修多视聚合的正确性，conf_head 决定哪些深度进点云**；中心、范围、候选数、先验入口全部进 backlog，等这个完整候选赢了之后再做回顾性消融。
